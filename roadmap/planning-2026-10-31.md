# clauderoadmapwrangler — planning session 2026-10-31 (portfolio survey, research pass, domain map, interview record)

This file is the record of the roadmap-planning session for a new project: a Rust desktop application
that keeps track of the owner's development projects (folders under one `DATA\` directory, most of them
run as session-sized roadmap briefs executed by Claude Code) and mirrors the owner's Claude Code workflow:
one view of every project's next brief, session launch with a chosen model and effort, inter-session
to-dos for the owner, optional automatic chaining of briefs, repository and backup status, badges,
sorting, history graphs, a chat pane to Claude Code, an in-session decisions pane, an account usage meter,
and later a mobile-friendly view over the owner's tailnet. It holds (1) the verified state of the machine
and the portfolio, (2) the research pass over the tooling, (3) the domain map derived from the owner's
brief, and (4) the interview record (questions, answers, resulting decisions). The roadmap (`README.md`
in this folder), `../DECISIONS.md` and `../CLAUDE.md` are written from it.

Portfolio-specific facts (project names, paths, states) live in `../private/portfolio-2026-10-31.md`,
which is git-ignored: the owner decided at the outset that the published repository must not describe
the projects the tool handles. Tracked files name a project only when it is already public.

### 2.2 The VS Code extension (2.1.314)

The extension registers a URI handler: `vscode://anthropic.claude-code/open?session=<id>&prompt=<text>`
runs `claude-vscode.primaryEditor.open(session, prompt)`, i.e. opens a conversation tab with that initial
prompt (`/install-plugin` is the other route). The `vscode://` protocol is registered to
`Code.exe --open-url -- "%1"`, so an external program can start a visual session with a prepared prompt
in the running window. Registered commands include `claude-vscode.newConversation`, `editor.open`,
`window.open`, `sidebar.open`, `terminal.open`, `createWorktree`, `renameSessionTab`. The cwd of such a
session is the workspace's first folder (the multi-root finding above). Alternative visual launch: a
Windows Terminal tab running `claude --ide --name … "<prompt>"` in the project folder, attached to the
one running VS Code window.

### 2.6 Convention variability across the eleven roadmaps (read-only survey, 2026-10-31)

Per-project detail is in `../private/portfolio-2026-10-31.md` §"Conventions". What a parser must cope with:

- **Three phase-table headers:** `# | Brief | Size | Depends on | Core | Done` (seven roadmaps);
  `# | Brief | Size | Depends on | Done` (two, the oldest house-style ones); `# | Packet | Size |
  Depends on | Status` (one, the packet style). Other tables also begin with `| #` (file lists,
  capability coverage, routines, glossaries), so the header row, not the prefix, identifies a phase table.
- **Done cells:** `☑ \`hash\`` (seven), bare `☑ hash` (two), several hashes joined by ` + ` (up to eight),
  a `◐` "done but not landed" state defined by one project, and `[ ]` / `[~]` / `[x] hash` in the packet
  style (also in its milestone headings). Hashes in one published project do not resolve (the repo was
  re-initialised on one commit at publication).
- **Sizes:** S 92, M 282, L 65 across all tables, plus re-scopes written into the cell (`S → L (re-scoped
  date)`, `S→M (owner escalated …)`, `S/M`); the packet style defines sizes in sessions. Core/stretch: 345
  core, 15 stretch. XS never appears.
- **Next EP = first unchecked row in table order, not the lowest number:** re-plans append rows into
  earlier phases (EP-164 … EP-173 inserted into P1–P3; EP-14 after EP-6; EP-8 before EP-7) and never
  renumber; the packet style splits into EP-4a/4b with parent files that have no rows.
- **"In progress" is implicit:** a brief file exists (often untracked) without a completion note while the
  row is still `☐`; the row is linked sometimes at pickup and sometimes only at completion; brief-note
  bullets may say "Done …" before the tick; a brief's own status line can be stale. During the survey
  three projects changed (a brief created, a row relinked, an EP ticked), so reads must snapshot and
  distinguish committed state from the working tree.
- **Brief cell:** the link may wrap the whole title, part of it, or be absent; D-refs sit inside or after
  the link text; titles are rewritten at pickup; rows are single lines up to 867 characters; no HTML,
  escaped pipes or merged cells. Depends-on cells carry ranges (`EP-6 … EP-12`, `EP-26–34`), prose
  ("all UI EPs", "everything") and annotations ("EP-3 (met)", "run before EP-21").
- **Phase headings:** `## Phase P0 —`, `## Phase 1 —`, `## R0 —`, `### M0 — … · [x] hash`; two-digit
  phases; status in parentheses ("done date", "charter", "placeholder; not planned"); phases without a table.
- **Brief notes:** `**Brief notes.**` followed by `- **EP-n.** …` bullets is the current form; variants are a
  prose paragraph with inline `EP-n:` segments for charter phases, `**Charters.**`, pickup-note blocks
  inside pre-written briefs, and no notes at all when every brief is pre-written.
- **Completion:** `> **Completion note (date).**` (the house form, with suffix variants such as
  "(date, EP-n verification)" and occasionally two notes per brief) vs a `##` heading, `> **☑ COMPLETE
  (date).**`, `**Status:** DONE`, `## Handoff payload (filled date)`, or a separate `docs/handoffs/EP-N.md`
  with `**Status:** … · **Date:** … · **Commits:** …`; some done briefs have no marker and some done rows no
  brief file.
- **Decision logs:** root `DECISIONS.md` with `**D-n Title.**` and `> **Addendum (date, EP-n).**` (seven
  projects; label punctuation `*Why.*` vs `*Why:*`), nested inside the package folder (two), a status-index
  table (one), domain ids `D-PROD-001` with no addenda (one), ADR files `adr/0001-*.md` (one), inline
  numbered decisions in the roadmap README (one).
- **Owner to-dos, seven forms:** `## Risks / open items` numbered lists with strike-through on resolution;
  `> **Parked.**`, `> **Handed on.**` and `> **Owner decisions (AskUserQuestion, date).**` blocks inside
  completion notes; an `owner-decisions.md` register (`OD-n`, `☐ **open — owner only**`) with a
  `pickup-gate.md`; an `open-questions.md` table (`OQ-x`, owner, decision point, effect if unresolved); a
  "Maintenance → Open items for the owner" list with date gates; an "Owner actions outside any brief"
  paragraph with "before EP-n" gates; handoff sections "Risks / notes for the next session" and "Next
  eligible EPs". No GitHub issues anywhere (zero on every public repo).
- **Model and effort per EP:** recorded nowhere. **Time per EP:** completion-note dates, the dates of the
  `☑` commits, free-text timings in notes ("About 20 minutes of build against M ≈ 1 h"), and retro tables
  in four projects (`| EP | Planned | Actual | What bit |`).
- **Commit patterns:** `<Area>: <summary> (EP-n, D-x)` + `docs(roadmap): record EP-n commit hash` in the
  five recent projects (with non-EP commits mixed in); `feat(pkg): … (EP-n)` + the record commit in the
  mature one; `EP-11: …` prefixes in the packet style; one squashed commit in the published Bevy project.
- **Existing checkers to learn from:** a PowerShell `roadmap-check.ps1` (header regex `^\|\s*#\s*\|\s*Brief`,
  hash regex `[0-9a-f]{7,40}`, note regex `^>\s*\*\*Completion note`) and two Python `roadmap_check.py`
  (brief-file regex `^EP-(\d+)-[a-z0-9-]+\.md$`, range regex, `◐` handling, header-block parsing). The

### 2.7 Claude Code documentation pass (code.claude.com/docs, read 2026-10-31)

- **Integration routes.** Official Agent SDKs exist for TypeScript and Python only; the documented route
  for any other language is the CLI as a subprocess with `-p` and `--output-format json|stream-json`
  (`stream-json` requires `--verbose`). The bidirectional control protocol (`control_request` /
  `control_response`: `initialize`, `interrupt`, `can_use_tool`, `set_model`, …) is shown in the SDK
  reference but not specified for non-SDK hosts; the community crate `claude-codes` (2.1.316,
  2026-10-31, Apache-2.0) types the whole protocol and versions itself after the newest CLI its live
  suite passed against. The crates.io package named `claude-agent-sdk` is **not** first-party (its
  repository link is dead). Anthropic's policy forbids third parties from offering claude.ai login or
  rate limits in their products; a personal tool driving the owner's own installed CLI is not addressed,
  which the public README should state plainly.
- **Billing and auth.** `--bare` never reads OAuth credentials (API key only) and is therefore unusable
  with the subscription; a set `ANTHROPIC_API_KEY` always wins in `-p`, so the tool keeps it out of the
  child environment (the same rule one project already decided). `claude auth status` exits 0 when
  logged in. Remote Control requires a claude.ai login and the default API base URL.
- **Print mode facts.** `--max-turns` and `--max-budget-usd` exist in the docs (the latter is a
  client-side list-price estimate, as is `total_cost_usd` in the result; subscribers are not billed in
  dollars); the installed `--help` lacks `--max-turns`, so flags are feature-detected, not assumed. Exit 0
  on success; in-run failures are printed as the result on stdout, so stdout is parsed even on a non-zero
  exit; SIGTERM exits 143 and leaves the turn unfinished (the documented graceful stop is: close stdin,
  wait, then kill). A `-p` run waits for its background work with a 10-minute idle cap
  (`CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS`). Print-mode sessions are hidden from the resume picker and
  `--continue` but resumable by id, so the tool pre-assigns `--session-id`. The `system/init` event carries
  `capabilities` and `claude_code_version`; `system/api_retry`, `permission_denied`, hook events (with
  `--include-hook-events`) and a final `result` (`stop_reason`, `permission_denials`, `structured_output`)
  follow. Hooks and `.mcp.json` servers run in `-p` with no trust dialog.
- **Human-in-the-loop without a terminal.** (a) Documented for the CLI: a PreToolUse hook returns
  `permissionDecision: "defer"`; the run exits with `stop_reason: "tool_deferred"` and `deferred_tool_use`
  (`id`, `name`, `input`); the host presents the question, then resumes with `claude -p --resume <id>` and
  the hook answers `allow` with `updatedInput`. Limits: only when the turn has one tool call; no timeout;
  ignored in interactive sessions. (b) SDK/protocol: `canUseTool` receives `AskUserQuestion` with
  `questions[]` (`question`, `header` ≤ 12 chars, 2–4 `options` with `label`/`description`, `multiSelect`)
  and answers with `updatedInput: {questions, answers}` (label, array, or free text). (c)
  `--permission-prompt-tool mcp__<server>__<tool>` names an MCP tool the host serves, but it cannot
  approve tools that require user interaction. (d) `--permission-prompts none` denies anything that would
  prompt. The docs frame all routes as relaying a human's choice. Setting `askUserQuestionTimeout` exists.
- **Hooks.** Events include SessionStart, UserPromptSubmit, PreToolUse, PermissionRequest, PostToolUse,
  Notification, SubagentStop, Stop, StopFailure, SessionEnd, PreCompact and many more; configured in
  `~/.claude/settings.json` (every project), `.claude/settings.json`, `.claude/settings.local.json`,
  plugins or `--settings`. Stdin JSON carries `session_id`, `transcript_path`, `cwd`, `hook_event_name`,
  `permission_mode`, `effort.level`; Stop adds `last_assistant_message`; Notification adds
  `notification_type` (`permission_prompt`, `idle_prompt`, `agent_needs_input`, `agent_completed`, …).
  **Stop fires per turn; SessionEnd fires once** (1.5 s budget, also on SIGTERM in print mode; behaviour
  on a hard kill undocumented). The VS Code extension fires the same hooks, so a user-level hook that
  posts to the tool's loopback server would see visual sessions too.
- **Usage numbers.** The only documented programmatic source is the status-line stdin JSON:
  `rate_limits.five_hour|seven_day.{used_percentage, resets_at}`, present for Pro/Max/Ultra only and only
  after a session's first API response, each window independently absent and dropped after its reset; no
  model-scoped weekly field is documented (the probe in §2.3 shows the Fable-scoped limit only on the
  undocumented endpoint). The status line also receives `cost.*`, `context_window.*`, `transcript_path`,
  `session_id`, `workspace.project_dir`, `effort.level`, `pr.*`; it runs after each assistant message and
  on `refreshInterval`; whether it runs in `-p` is unstated. `/usage` is interactive only. The settings
  key `autoContinueAtUsageLimit` exists.
- **Sessions and state.** Transcript path and 30-day `cleanupPeriodDays` as in §2.1; the JSONL format is
  declared internal and "changes between versions". Background sessions: `claude --bg "<prompt>"` cannot
  be combined with `-p`; a supervisor daemon keeps them alive after the terminal closes (not across a
  reboot: `failed`, then `stopped`); an idle unattached session stops its process after about an hour;
  **sessions move into `.claude/worktrees/` before their first edit unless the project settings say
  `"worktree": {"bgIsolation": "none"}`**, which matters for roadmaps edited in the main tree.
  `claude agents --json [--all] [--cwd]` is the documented interface: `state` (working, blocked, done,
  failed, stopped), `status` (busy, waiting, idle), `waitingFor` (permission prompt, input needed, …);
  `~/.claude/jobs/*/state.json` and `daemon/roster.json` are not to be parsed.
- **VS Code.** `vscode://anthropic.claude-code/open?prompt=…&session=…` opens a tab with the prompt
  **pre-filled, not submitted**; no parameter sets model or permission mode; window targeting is
  undocumented. Settings `claudeCode.useTerminal`, `preferredLocation`, `initialPermissionMode`,
  `claudeProcessWrapper`, `environmentVariables`. The extension bundles its own CLI (2.1.314 here) while
  the standalone binary is 2.1.261: two versions drift. `/ide` from an external terminal attaches through
  the extension's local WebSocket server (lock file `~/.claude/ide/<port>.lock`).
- **Remote Control, cloud, scheduling.** `claude --remote-control` (any interactive session; already on
  at startup here), `claude remote-control` server mode (`--spawn same-dir|worktree|session`,
  `--capacity`), `/rc`; the session runs locally, the transcript is stored on Anthropic's servers while
  connected, the phone gets push notifications. Cloud sessions run on Anthropic VMs (a local-only repo can
  be bundled and uploaded with `claude --cloud`, 100 MB cap, untracked files excluded); cloud scheduled
  tasks need a GitHub clone, so they do not apply to the local-only projects; the Desktop app has
  machine-local scheduled tasks; `/loop` is session-scoped.
- **Model and effort.** Aliases `default`, `best`, `fable`, `opus`, `sonnet`, `haiku`, `[1m]` variants;
  resolution `/model` > `--model` > `ANTHROPIC_MODEL` > `model` setting. Effort: `--effort low|medium|
  high|xhigh|max|ultracode` (`ultracode` is a mode that also sets `xhigh`; the keyword in a `-p` prompt is
  inert; the Workflow tool call then needs a `Workflow` allow rule, auto or bypass mode, or host approval);
  resolution `CLAUDE_CODE_EFFORT_LEVEL` > session pick > `--effort` > `modelSettings` (which rejects
  `max`). Fast mode runs on Opus models only. `--fallback-model` covers overload, not rate limits.
